## Proposed decisions and alternatives
Recommend one Go service and one local transactional relational authority, with SQLite as the proposed storage dependency, rather than a separate temporal graph database. Store typed relationship assertions in relational tables; graph is a domain/query view. Keep selected excerpts in the same authority for atomic capture. No independent object store is needed for the bounded text-only MVP. Database driver/version, durability settings, backup integration and deployment approval belong in GRO-24's governing ADR; this proposal does not certify a particular build.

| Workload | Relational baseline | Dedicated temporal graph | Semantic addition |
| --- | --- | --- | --- |
| Stable reference, alias, commitments | Direct IDs, typed indexes, deterministic filters | Adds no demonstrated benefit for fixture | Never replaces ID matching |
| A03 paraphrase | Lexical search may miss “resilience” versus “failed searches” | A graph cannot supply an absent supported topic match by itself | Passage embeddings plus lexical candidates; preserve exact source span |
| O→C→D and cycle | Bounded traversal of eligible typed rows with visited IDs | Natural traversal model, but another authority/transaction/recovery boundary | May seed identity, cannot invent edges |
| Valid/known history | Versioned assertions with two independent temporal predicates | Requires equally explicit correction/known-time semantics | Similarity ranks eligible evidence only |
| Unknown/denied/conflicting | Typed completeness/conflict results | Same obligations | Nearest neighbor is never proof of support or completeness |

PostgreSQL is a credible relational alternative if deployment needs concurrent administration or growth beyond declared bounds. It introduces a separate operational dependency for a single owner. A temporal graph adds synchronization and recovery obligations without measured fixture benefit. Reconsider either only against demonstrated limits and a new approved decision. No framework, global community summaries, reranker, agent loop or dedicated vector service is proposed for MVP.

Recommend hybrid lexical plus exact dense passage search for the paraphrase path, with deterministic structured paths for identity/time/commitments. Dense vectors are a rebuildable projection, never authoritative facts. Lexical-only remains the comparison control, not an assumed A03 pass. Model-expanded lexical queries are an alternative with fewer stored vectors but introduce generation variability and may still miss passages. Exact dense scanning avoids an additional approximate index in the proposed small corpus. If none passes A03/unknown tests, record failure and return the tradeoff to CTO/CPO; do not silently drop paraphrase recall.

## Identity and write invariants
Allocate opaque random UUID person/entity references on explicit creation; references do not encode names. Entity kind is person, organization, place, thing or event; O is an ordinary person. A particular book B has its own ID, separate from its title. Names are versioned assertions, with current/prior alias status and provenance.

Explicit M1 reference targets only M1. Unknown or deleted references fail actionably with no creation fallback. Renaming M1 to Morgan Vale retains Morgan Lee as a prior name. Resolving Morgan Lee therefore returns M1 and M2 as ambiguous. Name equality, semantic similarity and shared attendance never merge identities. MVP has no automatic merge. Unqualified ambiguous mutations do not commit any part of the requested domain change; return candidates with authorized disambiguating evidence and stable references. An unknown name needs explicit creation intent or clarification.

Treat natural-language interpretation as a typed candidate mutation. Validate target IDs, evidence locators, time precision, relationship types, required fields and version preconditions before commit. The model cannot supply authority, executable queries or tool commands. Host/client identity comes from authenticated session, not source text.

A capture transaction includes source/version/fragments, explicit entities and typed assertions, commitment and receipt plus projection work records. Unique retry key scoped to owner/client operation namespace plus canonical intent digest binds one intent. Same key/same intent returns the durable receipt; same key/changed intent returns conflict. Expected aggregate revision prevents lost updates. Serialize overlapping writes; concurrent identical retries converge on the same receipt. API owner defines exact MCP envelopes and canonicalization; canonical intent must include source content/locator, targets, time values and operation, never just raw wording. No durable domain change before validation. Crash before commit has no effect; crash after commit before delivery exposes the durable receipt on retry, with exactly one logical effect. Separate explicitly submitted captures are not deduplicated solely by text hash.

## Evidence contract and lineage
Logical records and required fields:
- Source: stable source_id, owner origin, mode (linked or archival), eligibility state/policy generation, recorded timestamp.
- Immutable source version: version_id, source_id, content digest, owner-supplied original locator and capture metadata. Locator is descriptive; never implicitly fetched.
- Fragment: fragment_id, version_id, text offsets plus supplied timecode/section locator, exact selected text and independent policy restriction if any. Split before indexing at any restriction boundary.
- Assertion version: assertion_id/version_id, typed predicate, subject/object IDs or typed value, supporting fragment IDs, attribution (speaker, reporter, unknown), valid-time value/precision, known interval, correction/supersession link and conflict group where applicable.
- Derivation: output ID/type, complete input fragment/assertion version IDs, transformation/model version, policy generation and source revision. Covers chunks, lexical entries, vectors, rendered answers/caches if retained.
- Operation receipt: stable operation ID, intent digest, commit revision, affected opaque references and inspectable eligible outcome.

Speaker attribution is independent from attendee membership and reporter identity. S1 00:10–00:25 attributes speech to M1; 00:30–00:35 stays unknown. S0c lists four attendees but supports only O/M1 conversation. Book lending/return and promise ownership are separate predicates/events, not inferred pairwise interactions. Topic mention supports discussion, not expertise.

Citation resolution returns the exact eligible source version and span. Fragment IDs are immutable within a version; revised text gets a new version/fragment. Do not pretend offsets in a new version locate the old text. Owner-supplied excerpt copies are the original evidence available to GRM; do not claim validation against a full transcript that was never supplied.

## Time, correction, precision and conflict
Store knowledge timestamps in UTC with monotonically ordered commit revisions for ties. Known intervals are [recorded_at, superseded_at); the state at inclusive cutoff K selects versions recorded at or before K and not yet superseded at K. Corrections committed at K apply at K; do not backdate knowledge. Valid intervals are start-inclusive/end-exclusive where precise bounds are supplied. No supplied end means open end, not proof of permanence. Unknown valid time is explicit.

Store date-only and month-only values as typed precision-bearing values, not fabricated instants. A month-only move means an event somewhere within September; interval enclosure is an indexing aid, not a September 1 assertion or evidence that every day qualifies. Exact-day questions return unknown day. Date-only due dates use configured America/New_York for the fixture and become overdue at the following local midnight; UTC server timezone does not decide. Completed promises stay excluded from open/overdue queries; no-date promises are never automatically overdue.

S2 initially supports Cedar Lab from September 1. S3 explicitly corrects its start only to September 15, replacing that account for later knowledge while preserving earlier versions. At September 10 / October 10 cutoff return S2's Cedar Lab account. At September 10 / October 21 cutoff return no supported role; no prior employer is inferred. September 16 supports Cedar Lab under both cutoffs with the corresponding start dates. S5's October 1 C/D conversation appears only after its November 1 recorded time. These predicates apply to every hop in historical path retrieval.

Newer evidence does not automatically win. S4 explicitly conflicts with the exclusive employer assertion: October 23 returns Cedar Lab and Birch Studio claims, sources and unresolved conflict. A correction targets an identified assertion/version and requires expected revision; an independent contradictory report remains independently inspectable. Retractions and corrections are knowledge events, not destructive overwrites until owner deletion requires erasure.

## Source eligibility and deletion
Manual selected excerpts are archival only when the owner explicitly authorizes GRM to retain that copy. Upstream loss alone does not revoke that authorization. Linked evidence requires an explicitly current owner-controlled eligibility grant; MVP does not fetch arbitrary URLs or claim automatic upstream permission detection. Link/locator alone is insufficient to ingest payload. Unknown eligibility withholds content. Owner revocation, expiry of the recorded grant, or deletion makes linked evidence ineligible; revoke archival authorization separately when desired. No broader monitoring or connector boundary is introduced.

S9 must be set up as genuinely revoked/expired under this policy, with “amber kites” solely in its content. Test it separately from an eligible archival copy whose original disappears. Suppress S9 text, topic, identifying citations, attributions and new export content. Regrant requires an explicit owner action and a new current eligibility version, never a stale job.

Deletion dominates known-time reconstruction. On S7 deletion erase its original and corrected text and both C/M1 attributions, topic and dependent assertion values from all accessible history/export/retrieval. Keep only an opaque reference, deletion status and deletion/recorded timestamps. Do not retain content hashes, identity links, topic labels, excerpts, intent payloads or revealing receipt outcomes for deleted material. A receipt may retain an opaque operation reference and unavailable outcome; retry must not restore payload. Independently evidenced unrelated facts survive. Mixed-source derivations are invalidated and regenerated solely from remaining eligible inputs; do not retain a contaminated summary under the same rendering.

Commit denial/tombstone and policy-generation increment first, atomically with removal of authoritative payload. Check current eligibility before hydration, provider disclosure, citation resolution and final response/export publication. Deletion acknowledgement means all service-accessible routes suppress content; physical cleanup of derivative files may follow only behind the deny gate. No service cache may bypass dependency checks. Reject delayed jobs with old source version/policy generation. MVP returns non-streamed results, and a publication/revocation barrier orders in-flight responses: output published before revocation is prior disclosure; no output authorized after revocation may contain that source. Cannot retract copies already delivered to an assistant or owner outside GRM; document that boundary.

## Retrieval flow, bounds and model boundary
Resolve explicit entity references first; ambiguous seeds return ambiguity. Classify request into exact, topic, path, history or commitment route; use bounded typed plans. Apply valid/known filters and current eligibility independently. For topic recall, rank lexical and dense candidates within that eligible set, fuse ranks, deduplicate by source version/span, then hydrate exact evidence. Only attributable qualifying passages produce a supported person. Return unknown speaker separately. Unsupported topics yield no supported person.

Proposed initial limits for approval: 10,000 entities, 50,000 assertion versions, 10,000 eligible fragments; 64 KiB UTF-8 per capture; at most 1,000 tokens per embedding chunk with offsets and attribution boundaries preserved. Query: 10 seconds service deadline, at most 100 candidates per retrieval branch, 20 hydrated fragments and 8,000 evidence tokens. Path: simple directed typed paths, maximum 3 hops, 1,000 examined relationship versions and 10 returned paths, with visited-ID cycle suppression. O→C→D must fit. No-path is valid only after complete eligible traversal within bounds; bound/deadline exhaustion returns incomplete/limit-reached, never “no path.” Return truncated topic coverage explicitly. Admission beyond storage/capture limits fails before mutation. These are proposed support limits, not measured capacity/latency promises.

Dense retrieval needs an approved local embedding runtime/model, pinned model identity, dimensions, tokenizer, similarity normalization and deterministic test settings. Model changes create a new projection generation; never compare incompatible vectors. A local inference endpoint can propose typed capture/query interpretations; all resulting claims require source linkage and deterministic validation. Prefer evidence records and constrained answer rendering over a separate free-form answer generator. The assistant can phrase returned evidence. No remote provider, credentials, paid runtime, telemetry or outbound content disclosure is authorized by this proposal. GRO-24 must bind a concrete local runtime/model/artifact and resource budget with Reliability/Security before approval; model compatibility and A03 quality remain unverified. This is an integration prerequisite, not a request to purchase a service.

If semantic projection is unavailable, exact/history/commitment routes may still work. Topic requests return explicit unavailable or clearly labeled lexical-only partial coverage; they cannot claim an exhaustive negative. Inference failure before a capture candidate is validated produces no mutation. No external inference provider is required for interruption injection.

## Visibility, export and recovery agreement
One relational commit is authoritative. Read a consistent content revision plus current policy at publication. Semantic work records are committed with capture; projection publication checks version and eligibility. Receipts distinguish durable capture from semantic readiness. A newly committed source is immediately available to exact lookup; topic search with pending projection must disclose incomplete coverage or wait within deadline. During rebuild use the old generation only for still-current eligible versions and disclose uncovered revisions. Do not expose half a capture or claim indexing success before publication. Content-free logging only; stored query/response history would itself require deletion lineage, so do not retain it in MVP.

Propose native export format grm-native/v1: UTF-8 JSON manifest plus typed record collections, including stable IDs, eligible source versions/fragments and locators, entity kinds/names, attributed assertions, valid-time precision/intervals, knowledge versions/correction links, relationship direction, commitments/state transitions, configured timezone and allowed opaque tombstones. Include export snapshot revision and format version; references must resolve or carry an explicit unavailable record. Never export embeddings as authority, credentials, deleted payloads or revealing deleted receipt bodies. Unknown major versions fail closed on import/restore. Validate unique IDs, referential integrity, interval/precision types and checksums before activation. Preserve unknown/unavailable distinctions. Backups are distinct from portable export.

Recovery requirements submitted for reconciliation with [GRO-28](/GRO/issues/GRO-28): restore B0 offline; apply a deletion/revocation ledger newer than B0 before opening any read, export, model or projection route; discard/rebuild derived indexes; validate references and rerun probes before activation. If a current trusted ledger or recovery epoch is unavailable, block usability. A warning with live S7 content fails R2. Ledger contains only permitted opaque deletion metadata plus required non-content revocation control state; it must not preserve S7 attribution. Reliability owns backup consistency, ledger survivability/rollback detection, migration and physical cleanup procedure. Old owner-held backups may still contain bytes and need documented removal; serving them is forbidden until reconciliation. No claim of automatic secure erasure of every storage medium.

At this writing GRO-28 exposes only its plan, not a recovery proposal. Therefore the ledger mechanism, restore activation guard and concrete runtime remain explicit integration dependencies, not agreed cross-owner decisions. Parent must reconcile them before documenting approval; this contribution can complete with that adverse evidence.

### Immutable pin protocol, replacing moving names at deployment
A model name is selected above; revision 2 intentionally specifies an immutable pin protocol rather than inventing unverified file hashes. No automatic latest, main, tag-only, colon-quantization alias or runtime Hugging Face fetch is acceptable in an installed release.

Before implementation starts, the governing documentation PR must include a reviewed dependency identity manifest produced by read-only metadata resolution: (1) exact full llama.cpp Git commit plus source archive hash and MIT text identity; (2) full publisher repository commit for each chosen model; (3) exact filenames, byte lengths and SHA-256/LFS object identities for BOTH Qwen shards and the Nomic F16 file; (4) associated upstream config/tokenizer/template/license revision identities; and (5) the selected compiler/CMake/native CPU build recipe identity and JSON-schema grammar support reference. Resolve the chosen model families/quantizations only, never choose a different model opportunistically. Treat publisher metadata hashes as expectations, not verified local bytes.

After architecture approval, artifact acquisition/build must verify those bytes, record executable/shared-library hashes, build flags and target instruction set, and reject missing shards or hash mismatch before service readiness. No executing remote model repository code and no runtime conversion is needed: use publisher GGUFs directly. A release manifest also pins extraction/query prompts, allowed typed-plan schemas, tokenizer/template bytes and every sampling parameter. Qualification consumes this exact tuple. Any changed model, tokenizer, quantization, pooling, template, grammar or executable starts a new qualification/projection generation. A fixed version update does not authorize a new provider or data destination. Actual full commit/hash values have not been asserted or manufactured here; this bounded manifest protocol is the selected identity mechanism requested by GRO-24.

### Same-host endpoints and trust boundary
Both native model processes run on the same Ubuntu Server 24.04 LTS x86-64 machine and owner-only installation as the one active stdio Go server. Propose explicit loopback endpoints 127.0.0.1:18081 for planning and 127.0.0.1:18082 for embeddings, with separate random local API secrets in owner-only files. GRM has a fixed allowlist for those literal endpoints; no URL from the caller, source or model can replace them. Only the Go domain service writes SQLite. The third-party model processes have no database, export, MCP-tool or mutation authority.

Require local model paths, offline mode, outbound-network denial for inference processes, loopback-only listeners and API-key enforcement. Disable web UI, tools/agent mode, MCP proxy, tunnels, automatic model fetching, router mode and remote fallback. Reject redirects/proxy settings that could move traffic off-host. The selected runtime's server docs expose offline, API-key-file, pooling and generation controls; qualification must verify effective behavior of the pinned build rather than trust defaults. [Server controls](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). Installation does not turn either endpoint into the owner's primary assistant; API/Security retain the separate all-local host choice and trusted deletion authorization.

Recheck source eligibility before each model request. No private prompt/output logging, persistent prompt cache, slot-save files or query history; do not fine-tune on owner content. Discard request buffers and clear/restart model slots after each request where the selected build cannot guarantee clearing. On deletion/revocation, cancel dependent jobs, clear model slots and restart model processes before acknowledgement if private context may remain reusable. Physical RAM forensic erasure is not claimed. Publication still uses the existing current-policy barrier, including in-flight cancellation.

### Fixed execution settings and context accounting
Use CPU-only native inference, GPU offload zero, one slot per model, no speculative decoding, no continuous batching and no concurrent request batches. Pin eight inference/prompt-evaluation threads for qualification on the hardware profile below. Warm both model processes before reporting inference-ready; a cold start may take up to a separate 120-second startup readiness budget, after which service reports unavailable. Cold start is not hidden inside an already accepted 10-second query.

Planning model: context allocation 8,192 tokens, FP16 K/V cache, temperature 0 (greedy), seed 42, top-k 1, top-p 1, min-p 0, repeat penalty 1, no dynamic-temperature/mirostat/other stochastic or adaptive samplers. Use pinned publisher chat template, schema-constrained JSON and a fixed versioned system instruction. No model tools and no repair/replanning loop. One planning call per prepare or NL query; malformed, truncated or unsupported-schema output fails actionably with no domain commit. Go validation still checks IDs, ambiguity, locators, time semantics and authority. Greedy generation and a seed reduce variation; they do not promise bit-identical output across CPUs/builds. Freeze CPU/backend/thread settings for comparisons and grade semantic facts independently.

Prepare permits up to 7,168 total prompt tokens including source text, instructions, schema and candidate identity context, reserving 1,024 completion tokens. NL query planning permits up to 2,048 total prompt tokens and 256 output tokens; it plans from the request/schema and bounded authorized identity context, not a generated synthesis of every evidence passage. Reject overflow before model execution, with an actionable request to submit smaller excerpts or disambiguate; never silently truncate source material or a candidate list. The 64 KiB whole encoded MCP request cap still applies independently. A request below the byte cap may exceed the tokenizer cap; no assumption of four bytes per token.

The 8,000 evidence-token/20-fragment allowance remains an upper bound for grounded structured results, counted with pinned Qwen tokenization and also constrained by the <=64 KiB response including text/structured duplication. It is not permission to exceed the planning model's context. Evidence rendering is deterministic; GRM does not send that whole evidence allowance through a second generative answer call. Natural-language input interpretation stays in GRM.

Embedding model: context 2,048, no RoPE extension, one passage/query per batch. Split passages at attribution/policy/structure boundaries into fragments whose fully encoded prefixed input including special tokens is at most 1,000 Nomic tokens; reject oversize query embedding input rather than silently truncating it. No overlap across independently governed boundaries. Preserve offsets back to exact original text. Cap eligible indexed fragments/vectors at 10,000, one vector per fragment. Query/fragment token counts use Nomic's pinned tokenizer, not Qwen's. Rebuild vectors when this encoding contract changes. Deterministic forward embedding has no sampling; record CPU numeric tolerances and stable rank tie handling.
