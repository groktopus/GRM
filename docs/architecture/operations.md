# GRM deployment, portability and deletion-safe recovery proposal
Status: proposed architecture contribution for GRO-24; not approval, implemented behavior, or recovery evidence. Author: Reliability Engineer. Date: 2026-11-21. Version: proposal 2. Refined against GRO-24 architecture-decision-reconciliation revision 4ebf319a-8eb8-4ce9-9b9b-248483bf5a60.

## Authority and scope
Read canonical [GRO-21 grm-mvp-definition](/GRO/issues/GRO-21#document-grm-mvp-definition), revision 20d061ee-ed64-4f9b-8ecd-ae2854a69219, in full, including R1–R6. Read repository AGENTS, CONTRIBUTING, product decisions, ADR index, ADR0001 and Go standards at checkout 4973371a69c7dbe225cef666a73f901de57245da. Only language has an accepted ADR. This proposal supplies concrete choices for Systems Architect integration and CTO ratification. A maintainer must approve and merge governing documentation in a documentation-only PR before implementation. No repository changes, configurations, prototypes, paid dependencies or outreach were made.

The boundary is one owner's assistant, GRM's Go backend, local durable state, owner-controlled backup media and a separately maintained deletion authority. No multi-user service or automatic outreach. The owner validates recovered private data; platform implements infrastructure; SRE defines exercises and records restoration evidence; CTO owns cross-component decisions and engineering quality. All GRM-owned workers and administrative executables are Go. Third-party engines/runtimes are exempt from that language rule only, not from architecture review.

## Recommended operational shape and alternatives
Recommend one unprivileged Go process, local transactional SQLite storage, all source bytes and selected excerpts in the same database transaction as domain effects and replay receipts, and reconstructible retrieval indexes in a separate subdirectory. SQLite uses WAL, synchronous FULL and foreign keys enabled on every connection; startup verifies these settings before serving. No independent graph/vector service, queue, cluster or background inference runtime is required by this proposal. Retrieval semantics and model/provider selection remain the architect's integrated decision; a model-dependent design cannot claim core installation complete until its destination, resource requirements and failure behavior are approved.

Proposed first supported environment: Ubuntu Server 24.04 LTS, Linux x86-64, local persistent ext4 storage, one OS account owning GRM state, system clock synchronized, explicit owner timezone America/New_York in the acceptance fixture. This is a proposed qualification target, not a compatibility claim. Test one pinned OS point release/kernel, Go release/toolchain, SQLite library and MCP SDK at release; record exact versions and hashes. Release pins must be chosen and reviewed during integration, rather than invented in this document. No Windows, macOS, ARM, NFS/shared filesystem, ephemeral container filesystem, multi-writer process or unattended failover support initially.

Recommend local MCP stdio: an approved assistant host launches/connects to the single supervised GRM process through a local authenticated OS boundary. Exactly one host-launched stdio server/session owns an exclusive installation lock for its entire lifetime. A second process/session is unsupported and rejected before database access or domain mutation; no daemon or cross-process session sharing is implied. Exact host and process ownership integration must be bound in GRO-24: host must exercise capture, query and correction and enforce that unauthorized OS principals cannot connect or read state. If the selected host requires a network transport or an always-running daemon, CTO must explicitly revise this transport choice and document authentication before implementation. Never silently open a listener. No particular host/version has been tested or qualified here; host qualification is a release-blocking integration gap, not a reason to expand access now.

| Option | Disposition and tradeoff |
| --- | --- |
| Single binary + embedded transactional database | Recommended: smallest dependency set and one recovery unit; requires careful durable commit and deletion gates. |
| Container on same host | Deferred packaging alternative: useful isolation but adds runtime, volume and UID mistakes; qualify separately with identical persistence/recovery tests. |
| Go + PostgreSQL plus external vector/graph services | Viable only if integrated retrieval needs it; more credentials, backup consistency and failure modes than MVP currently justifies. |
| Local third-party model runtime | Possible privacy-preserving dependency but hardware/model footprint needs a separate declared envelope; not smuggled into a 2 GiB baseline. |
| Hosted inference | No default authorization. Any proposal must list exact private-data destinations, secrets and costs and return boundary/scope tradeoffs to CTO/CPO. |
| Replication/HA cluster | Deferred: does not solve logical deletion or corrupted backups and increases single-owner operating burden. |

OS, local filesystem, SQLite and pinned timezone data are upstream dependencies; assistant is downstream. Backup media and deletion authority availability constrain recovery. Content-free logs are retained for at most 7 days. No private record in logs, crash reports or metrics. Log opaque operation IDs, outcome codes, durations, queue counts, version/checkpoint IDs and gate state. Counts/checkpoints remain private operator metadata. Secrets live outside exports/backups in owner-readable credential storage; release manifests enumerate actual network destinations, ideally none from GRM core. Encryption at rest and encrypted removable backups are owner setup requirements; losing encryption keys makes the affected recovery source unusable.

## State, operations and bounded failure behavior
Proposed state inventory: authoritative database (identities, relationships, evidence eligibility, valid/known times and precision, commitments, operation outcomes); reconstructible indexes; administrative metadata; credentials; independent deletion-authority directory. The deletion authority is not a content archive. Retry outcomes must be sanitized after deletion so a replay cannot return erased content.

Every mutation has an owner-namespace operation identity and whole-input exact/default-normalized equality for prepare and commit. Changed text or choices with the same identity conflicts; fuzzy semantic equivalence is forbidden. While eligible, validated input comparison material may be retained only under the approved privacy policy. Store the identity, comparison material, durable effect and content-safe receipt in the same database transaction. Retain operation identities for the life of the dataset; quotas stop new writes rather than silently expiring replay guarantees. Matching retries return the same logical result; different input with the same identity returns an explicit conflict without a second write. Within the supported session/restart, matching retries serialize under a uniqueness constraint: one logical commit, equal outcome references. R4 separate-session concurrency is unsupported and must be rejected without mutation. A new operation ID with same natural-language text is a new intent, not an implicit deduplication promise. Updating nonexistent/deleted references or invalid required inputs fails before mutation. Tombstones prevent reference reuse.

Precommit interruption: inspect database before retry; no new interaction, promise or completed operation exists. Prepared external/model responses confer no authority or durable success. Retry may safely execute once. Postcommit/lost reply: inspect state before retry; exactly one capture/commitment and one committed operation already exist. Retry returns its outcome without extraction or mutation repeating. A timeout after uncertain commit returns “outcome unknown; retry this operation identity,” never success or an invented rollback. Startup performs transactional recovery before accepting requests. If integrity cannot be established, remain closed.

Capture validates and atomically commits the intended event, evidence, promise and operation receipt; reject unsupported partial captures actionably. Derived indexes update after authoritative commit and carry checkpoints. Queries cannot use stale entries that bypass deletion/eligibility filters. While rebuilding, return explicit retrieval unavailable/incomplete for affected query classes; direct authoritative reads may remain available if their authorization and completeness can be proved. No-path is allowed only after complete bounded search. Query failure may return an explicitly labeled partial result with missing work identified; never claim absent evidence just because a dependency failed.

Initial qualification budgets (proposed limits, not measured capacity): host 2 vCPU, 2 GiB RAM, 10 GiB free local disk for corpus and temporary restore space; process resident memory target at most 1 GiB. At most 2 executing requests, 8 waiting requests, 1 transactional writer; excess rejected busy/retryable before mutation. Encoded request at most 64 KiB; no unbounded transcript ingestion. Qualification dataset at most 10,000 entities, 50,000 assertion versions and 10,000 eligible fragments, with an additional 1 GiB logical data ceiling; exceeding supported totals rejects new capture actionably, while deletion/export/recovery remain available within dedicated administrative capacity. Test actual disk needs including journals, export, restore and index rebuild; 10 GiB is a starting envelope, not a guarantee.

Traversal: at most 3 hops, 1,000 examined relationship versions and 10 returned paths; cycle detection on stable references; query deadline 10 seconds. The O→C→D corpus must complete. Disconnected Z yields complete no-path; deliberately exhausted depth/node/edge/time bounds yield incomplete/limit-reached, never no-path. Prepare deadline 30 seconds; commit deadline 10 seconds before outcome reconciliation; storage lock wait at most 2 seconds within that deadline. Administrative restore/export has explicit progress and cancellation rather than the interactive deadline. Dependency calls, if approved, share the caller deadline, at most 5 seconds each and one retry for safe reads within total budget; no blind external mutation retry. Repeated failure is surfaced; no unbounded queue or retry storm.

Reserve administrative headroom: stop ordinary writes below 20% free disk, report low space, permit only bounded safe reads and recovery/deletion operations whose durability can be guaranteed. If disk cannot durably record a deletion, block affected/all content access rather than falsely acknowledge. I/O failure, corruption or lost deletion authority fails closed. OS OOM/crash is handled by restart recovery; measured memory excess blocks qualification. One active stdio session only; a second process/session is rejected without mutation. Responses are at most 64 KiB including structured/text duplication, at most 20 hydrated fragments and 8,000 evidence tokens. Exact dense search uses no separate vector database. The base host budget excludes inference: a named no-cost local runtime/model and its separate CPU/RAM/disk/context budget must be bound by Data and CTO before governing architecture approval. No remote fallback or hardware purchase is implied.

## Eligibility, time and deletion
Linked-source content requires currently established access eligibility; eligibility unknown or revoked excludes passage, identifying citation, derived answer and export. An expressly owner-authorized archival copy remains eligible after upstream disappearance unless its authorization is revoked. Restore never upgrades linked material into an archival copy. S9 revocation must suppress “amber kites” through every route; an independent archival-copy case is tested separately. Restore must reestablish eligibility or treat it as unavailable. Source content, including S8 hostile instructions, cannot authorize actions.

Persist owner timezone explicitly, including in export. Date-only due date stays due through that local day; open becomes overdue at start of the next local date. Do not add 24 hours to a UTC instant or infer timezone from host settings. For America/New_York and due 2026-10-05, test 2026-10-06T03:59:59Z due today/not overdue, 04:00:00Z overdue, 04:00:01Z overdue. Completed promises remain excluded at all three points; undated open promises never automatically overdue. Add DST spring/fall dates, host timezone disagreement, and restoration onto a UTC host; local-date meaning must survive. Preserve both valid and known times and uncertainty; A09 deletion outranks historical reconstruction.

Recommend an independent durable deletion authority with dataset lineage ID, monotonic deletion sequence and integrity-protected checkpoint. Content-free deletion entries retain only opaque reference, deletion status and deletion/recorded timestamps as R1 permits; sequence/checkpoint is system metadata without source content. No excerpts, topics, names, identifying attribution or old response bodies. Integrity protection detects alteration; it does not prove freshness. Owner's current authority location and latest checkpoint must be maintained independently of backup B0.

Deletion uses a persistent serving gate: fence all content access, drain/cancel outstanding responses, durably record deletion in authority, apply it transactionally to authoritative content and all derived references, erase cached receipts, discard/rebuild indexes, then verify and reopen. Acknowledged deletion means durable authority plus enforced removal. If crash occurs after authority append but before data purge, startup replays deletions before serving. Any uncertainty leaves the gate closed. Deleting a source removes its historical attributions as well as current content, but preserves unrelated supported records. Disallow automatic source re-ingestion with the deleted reference. No guarantee of physical forensic erasure from SSDs or copies outside owner control; operator guide must distinguish logical inaccessibility, retained media and deliberate media destruction.

## Native export v1
Recommend a documented UTF-8 JSON Lines bundle, format identifier grm-native and major version 1, with manifest and named record streams. This is a proposed contract for architecture integration, not file/config code. Manifest includes dataset lineage, export format, schema version, application version, owner timezone, consistent committed snapshot/checkpoint, eligibility-policy version, file counts and SHA-256 checksums. Records preserve stable references, entity types/names, relationships and provenance, evidence references and eligible archival excerpts, commitments/state/date precision, valid/known time histories, corrections and permitted content-free deletion notices. Unavailable external links are marked unavailable without content leakage; dangling references are enumerated with reasons or cause export validation to fail. Credentials, logs, caches and deleted/ineligible content are excluded.

Export takes a consistent snapshot under the current deletion authority. A deletion concurrent with export fences and invalidates any unpublished export containing that content; publish only after revalidation at the latest deletion checkpoint. A previously delivered owner export is a private copy the owner must remove separately. Export writes to a temporary restricted location; final artifact appears only after counts/checksums/reference and deletion checks pass. Failure leaves no apparently complete artifact. Unknown major versions rejected; optional unknown fields within v1 can be retained/ignored only under documented compatible rules. Roundtrip into a clean isolated instance preserves logical references and history; do not imply CSV interoperability. Import/restore of any content-bearing bundle goes through the same deletion gate; v1 export is portable data, not a bypass around restore authority. Native export does not replace a tested database backup.

## Backup and recovery objectives
Recommend owner-triggered daily consistent snapshots and before upgrades, with 7 daily and up to 4 weekly encrypted copies only while each remains no older than 30 days, at least one on disconnected owner-controlled media; no purchased service required. Freshness warnings expose last verified recoverable commit time, not merely backup-job completion. Backups include database, eligible evidence, schema/application manifest, checksums, lineage and deletion checkpoint; reconstructible indexes may be omitted. Export/backup failures are actionable and preserve prior good copies. Deletion authority requires independent protection; never overwrite its current state with the authority captured inside an older backup. Delete obsolete backups/exports deliberately under the retention policy; immutable media containing erased content stays sensitive and cannot be made safe by a warning.

Proposed objectives for this non-critical personal CRM: process restart within 5 minutes with no lost acknowledged commits on intact healthy storage; host/media loss or logical-corruption restore within 4 hours after clean host, keys and authoritative deletion state are available, with at most 24 hours lost ordinary updates under daily verified backups. Measure outage-to-validated usable service and separately prerequisites/wait time; total outage may exceed target. These are engineering targets requiring CTO ratification and exercises. Daily snapshots do not establish a 24-hour recovery point if a snapshot fails: report the actual newest verified recoverable commit and gap. Deletions have a stricter condition: zero acknowledged deletions reversed in any usable restored instance, even if other updates are lost. Missing current authority makes RTO unbounded until safely reconciled. Faster HA/continuous archival would add cost and complexity unjustified by current product scope; slower recovery burdens owner recall. No availability percentage or proven RTO/RPO is claimed.

## Exact B0 old-backup restore procedure (including lost ledger)
1. Owner stops the serving process and clients. Platform/SRE records incident scope, immutable backup identity, checksums, schema, lineage and commit time. Preserve failed state read-only for diagnosis under private access. Provision a separate empty restore directory; do not replace the live directory in place.
2. Start only administrative quarantine mode: no MCP tools, queries, evidence reads, historical endpoints, exports, index-backed previews or background dissemination. Gate defaults closed before any database opens. Candidate state is not usable content.
3. Validate backup checksums and schema, then restore B0 to quarantine. Reject unknown version, corrupt data or mismatched lineage. B0's own ledger/checkpoint cannot establish that there were no later deletions.
4. Obtain the current independent deletion authority and its freshness witness from the surviving live installation or owner-maintained current recovery authority. Validate lineage, monotonic sequence, integrity and continuity through the owner's latest recorded checkpoint. Restore must require this check even when B0 appears “clean.” A same-age ledger copy beside B0 is insufficient. If current deletion freshness cannot be established, go to step 8.
5. Replay all current deletions, including S7 deleted after B0, into candidate authoritative state. Remove evidence, source-derived assertions, historical copies, cached operation replies and any disallowed identifying metadata. Reevaluate source access, exclude S9 if revoked, discard every old index/cache, and rebuild only from eligible undeleted content. Fence concurrent writes/deletions until final checkpoint validation; any new deletion restarts final validation.
6. Validate structure/checksums against B0 first, then reconcile expected differences against deletion operations; exact post-purge byte equality to B0 is wrong. Verify stable references, links, commitment states, valid/known times and retained history for unrelated data. Run S7 current/topic/history/evidence/export probes: no “cobalt origami,” excerpt or attribution; only permitted content-free notice. Run S9 probes and full undeleted A01–A09 semantics where applicable. Record counts before/after, expected removals and discrepancies.
7. Owner/data validator reviews recovered data and loss interval, SRE records recovery evidence, platform atomically promotes validated candidate. Serving gate opens only when current authority/checkpoint and validation receipt match candidate. Restart must preserve this gate decision. Rotate/reconfigure credentials separately, reconnect approved host, rerun smoke checks. Any discrepancy returns to quarantine. Reopening is a validated state transition, never a warning checkbox.
8. **Lost or unverifiably stale deletion authority:** keep all B0 content quarantined and unavailable through every normal interface. No “accept risk and expose backup” option. Owner may reconstruct the complete current deletion set from independently current trustworthy records and validate its coverage, then resume step 4. Recollection or backup age alone cannot prove completeness. If completeness cannot be established, abandon B0 as a source of usable content: initialize a fresh empty dataset with a new lineage, and re-enter only independently supplied eligible information. Do not bulk copy uncertain B0 records. This sacrifices undeleted recovery rather than reviving deleted private content; record it as failed full restore with safe service reinitialization, not passing A12. Destroy or retain quarantined media under explicit owner-controlled private retention.
9. Delete quarantine temporary files and revoked exports according to the documented media policy; record completion without private content. Preserve content-free evidence receipts. An old binary or manual filesystem reader can bypass application logic; the supported procedure cannot promise safety against an owner deliberately extracting raw B0. Backup confidentiality remains essential.

This mechanism cannot simultaneously guarantee complete old-backup recovery and honor unknown deletions after every independent record is lost. That is an explicit adverse tradeoff for CTO/CPO. It does meet the required fail-closed observable outcome; a product claiming full recovery in that scenario would be misleading.

## Upgrade, migration, rollback and uninstall
Stop serving, verify a pre-upgrade backup and independent current deletion authority, check free space, and migrate a separate candidate with explicit source/target schema versions. No automatic downgrade or destructive in-place migration. Migration runs in quarantine, preserving operation identities, source eligibility, both times and precision; reapply current deletions and repeat reference/history probes before atomic promotion. On failure retain original untouched state and fail actionably. Rollback to an old binary is allowed only if it understands the current schema and deletion gate; otherwise restore a compatible backup through the full B0 procedure with current deletion authority. Never roll back the authority. Unsupported migrations refuse before modifying live data. Cross-host moves, native imports and reinstalls are restores, not shortcuts.

Uninstall has two documented choices: remove executable/host connection while retaining private state, or owner-confirmed data removal. Stop processes, detach host, revoke credentials, enumerate database/journals/evidence/indexes/temp exports/backups and authority media, then remove the selected copies. Keep authority while any older backup might still be restored; erase it last only when retiring that lineage and all recoverable copies. If immutable backup media cannot be erased, state retention explicitly and keep recovery quarantine requirements. Verify fresh launch has no record access and no worker remains. No automatic removal of unrelated assistant data or OS packages.

## Failure modes and expected degradation
Likelihood below is qualitative design judgment, not incident statistics.
| Failure | Likelihood / impact | Detection and exact behavior |
| --- | --- | --- |
| Crash or power loss | medium / high | Process exit; atomic recovery and replay inspect durable commit; never duplicate capture. |
| Disk full/I/O failure | medium / high | Free space and write errors; refuse ordinary writes; no false success, fence unsafe deletions. |
| Corruption or unknown schema | low / critical | Integrity/schema check; all content gate closed, restore trusted candidate. |
| Lost/stale deletion authority | medium / critical | Checkpoint unavailable/mismatch; all restore access blocked, step 8. |
| Index lag/failure | medium / medium | Checkpoint mismatch; shed semantic/path retrieval requiring it, preserve proven direct reads; disclose incompleteness. |
| Source revocation | medium / high | Eligibility decision fails; suppress content/citations/derived answers/exports. |
| Approved provider slow/down/malformed | medium / high | Deadline/typed validation; affected extraction/query fails or partial-labeled; no invented result or durable partial capture. |
| Host or MCP unavailable | medium / medium | Connection failure; local data persists; owner retries stable operation identity. |
| Concurrent replay/retry storm | medium / high | Queue/uniqueness limits; one effect, busy responses, bounded memory. |
| Keys/media lost | low / critical | Decrypt/check failure; no recovery from that copy, report loss. |

Core preservation priority is correctness and privacy, then eligible evidence recall/capture, then reconstructible indexes. No optional updates, monitoring, outreach or public ingestion is introduced. A10 is OMITTED: no queue, hint, retrieve, acknowledge or dismiss functionality; release states not implemented and QA records N/A with omission evidence. Reduced service is acceptable only while completeness/eligibility can be proved; uncertainty about deletion is an outage, not a stale-content fallback.

## Concrete denial authority and recovery-kit protocol (revision 2)
This section binds and clarifies all earlier references to “independent authority,” “freshness witness” and serving gates. It supersedes any earlier implication that an integrity-protected backup checkpoint alone is adequate. These are proposed design requirements, not an implemented or tested filesystem procedure.

### Locations and ownership
Use explicit absolute installation locations resolved by the owner at initialization; never infer a different path after a mount disappears. Illustrative synthetic paths:
- `/home/grmowner/.local/share/grm/install-A/`: owner-only directory (0700); `state.sqlite` plus SQLite-managed WAL/SHM, `indexes/`, `staging/`, and `install.lock`. No separate evidence files. Runtime files are owner-only (0600); no content on stdout except authorized MCP responses, no core dumps.
- `/media/grm-recovery/GRM-A/`: required current recovery kit on an existing owner-controlled independent storage volume, outside installation backups. Contains `denials.log`, `head`, lineage/format metadata and integrity key material protected by owner permissions and encryption. Missing mount is an error, not permission to create a replacement directory on the root filesystem.
- `/home/grmowner/.local/state/grm-witness/GRM-A/head`: current local witness outside backup/restore scope. It records lineage, sequence and chain head only. Owner must preserve a second independently current witness on another existing owner-controlled recovery location if recovery must survive loss of this host. No purchase or remote account is required or authorized here. Without surviving current witness, full host-loss recovery can be blocked.

The kit is the append authority; witness heads detect stale substitution when at least one independently current head survives. Backups never contain authority keys or overwrite kit/witness locations. A kit copy captured with B0 is historical evidence only. SQLite has its own applied-denial checkpoint; installation restore cannot set external heads backward. Lock is an OS advisory exclusive lock held on the installation file descriptor, not PID-file presence. Only the server or exclusive administrative recovery process may hold it; lock release on crash does not mean serving is allowed. Administrative and server access also exclusively lock the kit; changing configured lineage/paths requires trusted local owner setup while serving is closed.

### Record and metadata boundaries
The authority has one ordered append stream of monotonically increasing denial transactions. A control envelope records lineage, sequence, previous control-record hash, random denial transaction ID, type and integrity authenticator. Its chain hashes cover allowed control metadata, never a source-content hash. The source deletion payload contains only opaque reference, deletion status and deletion/recorded timestamps. No source title, original input digest, excerpt, topic, attribution, participant name or identifying URL survives deletion. Sequence/integrity envelopes are system control metadata, not extra fields on the per-source deletion notice.

Revocation is a separate control-record type keyed by opaque eligibility/grant reference with deny status and control timestamp. It does not expand the allowed per-source deletion notice. Revocation is monotonic for that grant; recovery cannot replay an older grant as newer authorization. New eligibility requires a separately authorized new grant under the integrated Security policy, never a restore default. If an opaque grant/reference could itself expose identifying data, use a random non-semantic reference and strip its identifying mappings on deletion.

In SQLite and export, affected retry entries become content-safe reservations: opaque operation ID plus unavailable/reserved outcome, with no original input, plan, source hash/digest, response text or identifying result references. Erase all comparison material that can identify removed source content. Any retry of such a reserved identity returns explicit unavailable and makes no change, whether its supplied input matches or differs. It must not recompute a removed digest to reveal a match. A new authorized intent requires a new operation identity and cannot recreate a deleted reference. Purge prepared plans and model caches containing denied content too. WAL pages/old backups remain private physical copies until their supported cleanup/retention; logical access filters never read them as historical evidence.

### Append/checkpoint ordering
Denial begins only after API/Security's trusted local owner authorization bound to operation and exact plan; source text or model confirmation cannot authorize it. The ordering below applies to deletion and revocation:
1. With installation/kit locks held, stop admission, wait for all content-producing operations to finish or cancel them, close unpublished exports, and hold an exclusive in-process privacy barrier. Once the denial starts, no response can expose affected data. If an already delivered export exists, report it as an owner-held copy for disposal.
2. Create/update an installation gate marker to CLOSED using a temporary owner-only file, fsync the file, atomically rename on the same filesystem, then fsync its parent directory. Regardless of this marker's contents, every process starts CLOSED. Failure to persist the marker aborts serving, without claiming denial success.
3. Append a length-framed authenticated denial record at next sequence to the kit log; fsync the log before advancing its head. On first creation fsync containing directory. Write new kit head to temporary file, fsync, atomic rename, fsync kit directory. Never truncate a valid committed denial or reset sequence on quota exhaustion.
4. Advance the local witness and each designated independent current recovery witness by the same temporary-file/fsync/rename/directory-fsync protocol. Every designated required witness must be available and durably advanced before successful denial acknowledgement. A witness failure leaves service CLOSED and operation pending; it is not permission to roll back a denial already durable in the kit. This makes disconnected-kit/witness use an explicit availability cost: attach required existing media for denial completion and startup validation.
5. In one SQLite transaction, enforce all denials through that head, sanitize replay/prepared state, remove private content and derived assertions, and update the applied checkpoint. Commit under WAL/FULL; SQLite owns journal synchronization, not manual raw WAL edits. Foreign keys are enforced, and deletion may replace references with only allowed content-free notices where the integrated model permits them. Discard affected in-memory retrieval state and all stale persisted indexes; rebuild only from eligible data.
6. Verify consistency, denial probes, eligibility and checkpoint equality. A successful SQLite commit alone is insufficient. In particular all retained historical views, prepared/replay results and unpublished export staging must pass the denial filter.
7. Record validated OPEN checkpoint via the same atomic file/parent-directory synchronization and release the barrier only if kit, required witnesses, SQLite applied head and validation head agree. Acknowledge denial only after durable enforcement and required witness advancement. Lost reply returns the sanitized completed outcome; interrupted earlier stages return pending/unavailable until reconciliation. Open marker is evidence of a prior validation, never a startup authorization.

Control log/head initialization and any rotation use the same durability protocol. Do not compact away denials needed by any recoverable lineage backup/export; stop on space exhaustion. Rotation would need a complete authenticated snapshot of all denials plus chain continuity; defer rotation implementation until its exact protocol is reviewed. The authority's retained content-free state is not subject to the 30-day content-backup expiry.

### Startup, crash and mismatch table
Startup acquires exclusive locks, verifies actual ext4/local path and expected mount identity, opens control state first, validates lineage and authenticated log continuity, compares required witnesses, then opens/recover-checks SQLite with WAL/FULL/foreign keys and applies missing denials. It does not accept MCP requests until validation completes. Only an incomplete unauthenticated tail beyond the last valid log record may be discarded under exclusive administrative recovery; never discard a valid denial to match an older head. A witnessed sequence that is missing from the log is irreconcilable without a current copy.

| Crash/mismatch | Required next action; all begin CLOSED |
| --- | --- |
| Before durable denial append | No acknowledgement; retry trusted operation. Ordinary SQLite capture remains atomic as specified earlier. |
| After log fsync, before kit head/witness | Valid log tail is pending authoritative denial; advance head/witnesses forward, apply it. Never “undo” it because reply was absent. |
| Kit head ahead of witness | Reconcile valid chain forward only when existing witness is an ancestor; advance required witnesses before serving. |
| Witness ahead of kit, or hash differs at same sequence | Detect rollback/corruption; refuse activation, obtain current kit. Do not overwrite witness from kit. |
| Kit/witness durable, SQLite not committed | Replay all denials through current head, sanitize and verify. |
| SQLite committed, indexes/validation/open marker incomplete | Rebuild/discard indexes and rerun probes before activation. |
| SQLite head ahead of kit/witness | Refuse activation; external authority missing/stale, never infer current authority from B0. A surviving non-restored live state may aid owner reconciliation but cannot silently reset heads. |
| Marker says OPEN but any control state unavailable | Ignore OPEN, remain CLOSED. |
| Torn head file, bad authenticator, different lineage or missing required mount | Refuse activation; do not initialize replacement authority. |
| Lost response after full enforcement | Reservation/outcome confirms deletion without exposing prior payload; no second effect. |

### Owner current kit and rollback limits
At initialization owner records lineage and required kit/witness locations outside content backups. Each denial automatically advances all designated required heads before acknowledgement; operator status reports current sequence and which witness is missing, without source content. Before disconnecting kit/witness media, owner stops GRM and verifies matching heads; reconnect and validate before next startup. Content backups are dated/identified but are not freshness witnesses. Before migration or host replacement, stop the old instance, carry the current kit and current independent witness, and compare heads before importing content. Only one installation can serve that lineage; do not clone two active branches.

Hash chains and fsync detect corruption and rollback relative to a surviving newer head. They cannot detect a coordinated rollback of SQLite, kit and every witness, nor prove an owner-supplied snapshot is the latest after all current copies are lost. There is no trusted remote monotonic counter, hardware anchor, or independent service in this proposal. Owner confirmation is procedural evidence about custody, not cryptographic proof of freshness. If provenance/currency of all surviving heads is uncertain, do not accept an “I accept the risk” switch: keep B0 quarantined. A separately maintained current witness plus complete matching authority is required; an unauditable claimed reconstruction is insufficient. A lost kit with only a witness cannot supply the denial set; a lost witness with only kit cannot establish currency after host loss. Obtain a complete independently current matched recovery set or abandon B0 and initialize empty new lineage. This limitation may make the 4-hour target unattainable and may prevent undeleted recovery; report that adversely.

### Backup, export and evidence bindings
Take database backups using SQLite online backup API after quiescing mutations; never raw-copy an open database while ignoring WAL. Hold privacy barrier across the final denial-head validation and publication of the backup manifest. Database and manifest contain applied head but do not grant restore authority. Keep 7 daily and up to 4 weekly rolling encrypted backups only within a hard 30-day maximum; failed rotation must alert, and expired content copies cannot remain “rolling” backups. Owner-held immutable media/export disposal limitations stay explicit. Content-free logs expire at 7 days; denial control records persist as needed to prevent resurrection.
