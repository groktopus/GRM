## Decisions proposed and alternatives
| Decision | Recommendation | Alternatives and disposition |
| --- | --- | --- |
| D1 owner/client trust | One owner, separately enrolled local assistant clients, server-enforced capabilities. Default local process transport; authenticated owner-only launch and OS-protected IPC. No public listener. | Unauthenticated localhost listener rejects the trust boundary: another local process could use it. Remote HTTP/OAuth is deferred to separately approved transport architecture. |
| D2 provider | GRM-owned processing uses only an explicitly configured same-host local model runtime with no telemetry/outbound inference. No remote fallback or automatic provider discovery/download. | Remote free or paid inference changes disclosure boundaries and is excluded here. No-model operation is a useful diagnostic mode but cannot substitute for proving conversational capture/query on the declared host. |
| D3 model authority | Models emit bounded proposals, never policy changes, credentials, direct storage commands, or external actions. Server validates and authorizes every effect. | Prompt-only controls and a general agent with database/network tools fail the authority requirement. |
| D4 source policy | Distinguish linked material from an explicitly owner-authorized archival copy. Every derived fact retains its support set and current eligibility dependency. | Treating every link as an archive overretains; revoking every authorized copy when an upstream link disappears contradicts R3. |
| D5 history/deletion | Preserve correction history while eligible; deletion masks all historical and derived access immediately, then purges covered material. | Keeping private excerpts in immutable event history or hiding only current search fails A09. |
| D6 recovery | Separate current deletion ledger from data snapshots; restore starts quarantined and requires authoritative current ledger reconciliation. Unknown ledger freshness blocks usability. | Automatic snapshot restore or warning-only restore fails R2. Per-source cryptographic erasure may complement later designs but is not assumed sufficient for caches, shared facts or escaped copies. |
| D7 observability | Local, content-free operational events; no remote analytics, prompt traces or body logging. | Full debug traces create another private corpus and are excluded. |

Local inference is a proposed dependency boundary, not a selected runtime or proof of usable quality. Systems Architect must bind a no-cost same-host runtime/model, licensing, resource limits and supported assistant host. If none can satisfy the acceptance corpus, report an architecture feasibility gap to CTO/CPO; do not silently introduce remote inference.

## Assets, flow and authority/disclosure matrix
Protected assets: relationship facts, identities, excerpts, source associations, valid/known time, commitments, client credentials, policy configuration, deletion ledger, backups and exports. Even an entity association or topic embedding can reveal private content. Host root/admin, a compromised authorized assistant and already exported copies remain residual risks, not implied additional trusted users.

Flow: owner → enrolled assistant/MCP client → authenticated GRM boundary → policy/typed validation → proposal → validated transaction/storage. Retrieval flows from eligible storage candidates through support/policy checks to minimal evidence and assistant output. Optional same-host inference receives only eligible task-specific context. Recovery stays outside normal serving until reconciled.

| Actor/boundary | Authority | May receive | Must never receive or grant |
| --- | --- | --- | --- |
| Owner | Enroll/revoke clients, configure local provider/policy; authorize capture, correction, deletion and export | Eligible records and change receipts through configured client/operator surface | Source text cannot impersonate owner; content deletion cannot be bypassed by an old knowledge cutoff |
| MCP client | Delegated scoped read/propose/commit actions for this owner; no policy/admin privilege by default | Minimum eligible answer/passages requested under its capability; export only with separately authorized operation | Credentials, raw database/backup access, policy mutation, implicit corpus-wide disclosure |
| Source text, attachments, citations | None; data only, including quoted instructions | No tool credentials or privileged execution context | Cannot select provider/destination, enroll client, request export, expand retrieval, approve proposal or write |
| Model/runtime | Transform selected input to untrusted structured suggestions | Minimum eligible excerpt/query/context for the local task | Client secrets, storage keys, full corpus by default, network/tool/storage capabilities |
| GRM storage/service | Enforce validated operations and evidence/policy lineage | Required private data within owner's host boundary | Cannot count model confidence or client-supplied owner fields as authorization |
| Recovery operator/process | Owner-controlled offline restore and reconciliation | Quarantined snapshot and current content-free deletion ledger | Serving snapshot content before reconciliation; reset privacy policy from backup |
| Logs/export/backup | No independent authority | Logs: allowlisted events only. Export: currently eligible data. Backup: encrypted owner-controlled snapshot | Historical access or offline artifacts must not become an undocumented disclosure destination |

The assistant is a separate disclosure destination even if GRM inference stays local. A cloud-backed assistant may transmit returned passages to its provider under its own configuration. GRM cannot erase that provider's logs or the assistant conversation. Release documentation must name the tested host and its actual destinations; “local GRM” must not be advertised as end-to-end local. Prefer a local assistant host for the default demonstration. Enrollment must disclose what that host receives; a different host/provider requires explicit owner configuration, never automatic rerouting. This proposal authorizes no new third-party disclosure.

## Authentication, secrets and safe writes
Proposed process transport authenticates through an owner-only OS account/process launch and protected communication descriptors; clients do not discover an open port. The service must associate a client capability with a protected enrollment record/launch binding, not a self-asserted client name. If the selected SDK/transport cannot prove this binding, architecture must resolve it before code. Other OS accounts must be unable to read enrollment material or open the protected endpoint. Same-owner malicious processes are a documented limitation; separate client credentials/capabilities reduce accidental reach, not host compromise.

Enrollment is an owner operation outside source/model control. Proposed capabilities distinguish query, capture/propose, commit/correct, delete and export; ordinary conversational capture can commit under the owner's preconfigured capture capability. No routine permission ritual is needed for every ordinary note. Destructive deletion, bulk export and policy changes require explicit owner intent bound to the exact operation through a trusted owner channel; model text alone is insufficient. Architecture must specify how the supported host conveys this and must not rely on a model-generated “approved” field.

Keep any client token in an owner-only credential file or OS credential facility, never arguments, repository, prompts or logs. Reject missing/invalid/revoked credentials before object lookup, return generic unauthorized failure, perform no writes. Revocation invalidates subsequent use and in-flight delivery; restart does not resurrect grants. Rotation issues replacement, tests it, then revokes old access; exposure triggers immediate revocation. Backups do not restore active client grants or old secrets. The local model requires no paid API key.

Validate typed allowed operations, required fields, bounds, target existence, stable identity and current revision before commit. No SQL, shell, file paths, arbitrary URLs or tool names from model output become executable. Owner-selected excerpts are ingested as data; no automatic URL fetching or connectors in MVP. Ambiguous Morgan Lee does not select M1/M2; nonexistent/deleted references fail with no unrelated mutation. Proposal receipts show intended changes, support, uncertainty and stable references. Stale proposals fail/recompute after source eligibility, deletion or target revision changes.

Use an atomic durable logical mutation and receipt/retry record. A client-scoped retry identity binds canonical intent; changed intent yields explicit conflict. Concurrent same-intent retries yield one logical effect. Before durable commit, interruption leaves no effect; after commit but before response, replay returns the stored outcome after current-policy filtering. A retry receipt must not retain deleted note text; retain only content-free operation state and opaque references as needed. Never retry as a fresh operation silently.

## Current-policy and source eligibility
Every path must evaluate authenticated client capability AND current deletion state AND current source eligibility, independent of valid-time and known-time parameters. Apply before model context selection, candidate scoring disclosure, passage access, citations, caches, response assembly, export and restored-instance serving. Recheck at delivery/commit under a consistent policy version. A policy change during inference invalidates affected results; discard/recompute, never return stale context. Deletion/revocation acknowledgment is a barrier: later responses or resumed jobs cannot expose covered material. Already delivered content cannot be recalled.

Source classes:
* Owner-authored note/excerpt with explicit capture authority: archival copy, retained until owner deletion or explicit policy revocation. Upstream disappearance alone does not revoke it.
* Linked-only source: requires current verified access under the documented link policy. MVP need not fetch remote links; it may store provenance with unavailable content. No cached excerpt/embedding counts as a bypass. If access cannot be established, deny use and state unavailable.
* Owner-authorized archival copy of an external excerpt: records authorization and copy scope; disappearance of original does not invalidate it, but owner revocation of archival eligibility does.
* Unknown authority/provenance: ineligible for supporting private answers until resolved; model assertions do not establish eligibility.

Correcting attribution preserves earlier knowledge only until deletion. For shared derived records, remove support from deleted/ineligible sources and recompute from independently eligible sources. Do not delete unrelated entities or independently supported facts. Do not reveal removed source identity through a citation, inferred topic, snippet, score explanation or historical attribution. Empty or partial evidence is labeled unavailable/incomplete, not a proven negative.

## Deletion, retention and recovery lifecycle
| Privacy dimension | Proposed rule and enforcement |
| --- | --- |
| Purpose/classification | Private owner relationship recall and provenance only; all supplied content, identities and derived associations confidential; credentials restricted. No training, outreach, telemetry or unrelated reuse. |
| Lifecycle/retention | Primary records retained until owner deletion; transient inference context request-scoped and discarded on completion/cancellation. No retained provider prompts. Local operational logs expire after seven days; proposed rolling backups expire after 30 days. These durations require architecture ratification and owner documentation. |
| Access/isolation | Single-owner OS boundary and scoped clients; no tenant sharing or support access. Recheck current policy on every route. |
| Deletion | Acknowledgment only after durable deny state, affected-job cancellation and serving barrier. Purge covered primary/history/proposal/retry payloads, passages, embeddings, indexes, caches, temporary artifacts and queued work before reporting purge complete. Failed purge remains denied with actionable pending status. |
| Residency | Same owner-controlled host and local owner-controlled backup/export destination; no external telemetry, model endpoint or automatic backup upload. Actual paths/volumes must be documented by architecture. |
| Consent/authority | Owner-selected capture and explicit copy classification; no inferred permission from upstream text. Revocation changes subsequent behavior, invalidates pending proposals/results and removes affected retrieval. Owner authorization is an engineering permission, not a claim about third-party legal consent. |
| Recovery | Old snapshots quarantined, validated against current ledger/policy before any MCP/read/export access; missing reconciliation prevents usability. |

After S7 deletion, the only retained source-specific metadata is an opaque reference, deletion status and deletion/recorded timestamps. No excerpt, topic, speaker/person association, source title/path/URL, content hash, embedding or identifying attribution. Do not disguise content hashes as anonymous identifiers. Any operation records that would reveal deleted content/associations must be scrubbed too. Ledger integrity/version metadata may be system-level, but cannot add per-source identifying fields.

Proposed recovery procedure: stop serving; restore B0 to isolated local staging with no assistant/model access; load the current authoritative deletion ledger and current access policy from outside B0; verify integrity and freshness against owner-held current ledger checkpoint; apply all denials and purge/rebuild dependent indexes; verify undeleted records; only then enable serving. Ledger updates are durably checkpointed alongside deletion acknowledgment and protected separately from rolling snapshots. If ledger/checkpoint is lost, stale or cannot be authenticated, do not enable the restored corpus. Owner may supply a verified current ledger or discard the affected restore. An owner clicking through a warning cannot make S7 publishable. Architecture must choose concrete ledger integrity/freshness and crash behavior; an old snapshot's own ledger is insufficient.

Encrypted old backups still contain deleted bytes until replacement/expiry; logical deletion is not a physical erasure claim. Track these copies locally and report remaining backup retention, expire/delete GRM-controlled copies within the declared 30-day maximum, and ensure every restore uses reconciliation. New backups should contain only eligible data plus permitted metadata. OS snapshots, SSD remanence and copies outside GRM control require explicit operator documentation; no guarantee of forensic erasure is made. Old exports/assistant transcripts already held elsewhere cannot be recalled; warn at export time and document owner disposal. New native exports must filter history with current policy and preserve undeleted stable links/time dimensions, with content-free unavailable markers for removed support. Uninstall must identify data, secrets, logs, ledger, backups and exports separately; removing the binary alone is not data removal.

## Redacted logs and failures
Allow only event time, opaque request/client reference, operation category, allowed/denied outcome, fixed reason code, policy version, duration and generic destination category. Never log names, source titles/URLs, query/body/prompt text, citations, returned records, authorization headers, raw tokens, model output or content-derived fingerprints. Strip disallowed fields before writing, including panic/SDK/dependency error paths; no remote crash reporter. Logs referencing a deleted source must obey the stricter S7 metadata limit; do not retain joinable source/person attribution.

Bound input size, model context, traversal, runtime and concurrent work; Systems Architect supplies supported numeric limits. On local provider failure return explicit retryable failure where appropriate, without fabricated success. Query partial results label incompleteness and omit inaccessible evidence. A failed query is not “no results.” Policy-store failure denies access; deletion-ledger failure blocks serving/recovery. Sensitive dependency diagnostics remain fixed public reason codes with content-free operator detail.

## Verdict and bounded authority
Security accepts the one owner-only host-launched stdio session design as a proposal, subject to the exact conditions below. This replaces the earlier proposal for separately enrolled simultaneous clients; no token-based client identity or revocation system is required for this bounded process transport. MCP caller-supplied identity and confirm:true are not human authentication.

The trusted computing base includes the owner's OS account, selected assistant host, GRM executable, local model runtime, launch configuration and operator helper. Effective-owner authentication protects against other OS users and accidental unauthorized launches. It does not protect against root or malicious software running as the owner. A model with arbitrary same-owner shell/file control could forge an owner grant; terminal interaction alone is not a security boundary against that capability. Therefore the tested assistant configuration must expose only the GRM MCP tools for this workflow, without shell, terminal-driving or filesystem tools that reach GRM control state. Same-owner arbitrary-code compromise remains outside this boundary. If containment against such a client is required, this design is insufficient: require an independently enforced OS identity/privileged broker in a new documentation-first design. Do not claim terminal confirmation solves same-UID compromise.

## Single-session stdio launch and installation lock
1. Bind each installation to its configured owner UID. Reject effective UID mismatch, privileged/set-ID execution and unexpected owner/home/configuration before opening private data. This is single-owner authentication, not a claim that a process name establishes identity.
2. Protect installation/configuration/control/data directories with owner-only access; credentials, lock and control files likewise. Validate ownership and permissions and reject symbolic-link/path substitution at protected boundaries. Resolve executable, configuration, local provider and storage locations from protected operator configuration; source text/MCP fields cannot select them.
3. Acquire an OS-held exclusive installation lock before initializing the serving database or running recovery/migration. Hold it through shutdown. Lock-file presence is not ownership: a stale pathname after a crash must not permit two holders or permanently block safe recovery. Do not break a live lock on a timeout. Reject a second serving process before domain/proposal mutation or private tools/read responses. Same installation aliases must resolve to the same lock identity.
4. Only one stdio server owns SQLite writes and serves requests. Its in-process calls may be serialized; the exclusive lock is not a substitute for transaction atomicity. R4's multiple-session branch is explicitly unsupported: second host-launched server rejected without effects. Identical operation retries within the supported session and after restart remain mandatory.
5. Normal assistant access arrives only on protected host-created stdio descriptors, with no TCP listener or general IPC service. Stdout contains protocol only; stderr obeys content-free logs. Unsupported negotiated contract/protocol fails before private results.
6. Shutdown or terminate the process to revoke the active host session. Changing protected launch authorization prevents a subsequent launch. Restart/recovery does not import historical client grants. Any future concurrent host or remote transport needs new governing documentation.

This is sufficient for the proposed local-owner access model only after actual protected-launch and negative OS-user tests. Neither stdio nor possession of a lock establishes human intent.

## Ordinary capture versus destructive owner intent
Ordinary capture/correction/rename/completion follows GRO-26 prepare → inspect identities/actions → commit with the original operation ID, plan digest and resolved choices. Clear owner instruction may authorize the host-mediated commit under the documented host policy. Source passages, model output, confirmation flags and tool annotations cannot supply missing owner instruction. Ambiguous identity or changed/stale plan cannot commit.

Deletion requires an additional local owner grant. Export/restore remain separate authenticated local operator procedures; no MCP filesystem/export capability is introduced. A deletion-shaped action cannot be smuggled under capture/correct intent.

### Exact local terminal grant protocol proposed
A Go operator helper is a bounded operator action, not another serving session or database writer. It must not contend for or bypass the server's serving lock by launching another server. Proposed exchange uses owner-protected local control files, not a network endpoint:
1. Prepare persists the immutable, validated deletion plan and an owner-readable review snapshot in the protected control directory. Snapshot is server-produced and binds installation identity, operation ID, plan ID, exact plan digest, target opaque source ID, base revision, current policy epoch, expiration and a random current-server-session ID. It shows the actual deletion scope and derivative-removal consequences. Snapshot is private data with the same deletion/cleanup policy as a proposal.
2. Owner launches the helper directly in a local terminal. Helper reads this snapshot from the protected installation, never a caller-supplied replacement body. It renders scope safely, escaping terminal control characters and labeling excerpts as data. It opens the controlling terminal for interaction, rejects no-terminal invocation and piped/stdin confirmation, and requires an explicit typed approval naming the displayed operation ID. No credential or grant value is copied into chat/MCP arguments. The same-owner trust limitation above still applies.
3. Helper creates an atomic owner-only local grant record using a fresh unpredictable nonce, bound to that exact installation/session, operation ID, plan ID/digest, target, base revision and policy epoch. Lifetime is five minutes, capped by plan expiration. It durably writes the record before reporting grant saved. No wildcard, transferable or reusable approval. Digest must cover the complete executable plan and identity choices using API's versioned canonical plan representation; deletion has no unresolved choices. Digest alone is not authorization.
4. MCP commit carries the existing operation/plan fields, not a model-asserted grant. Server loads the local grant, verifies all bindings, freshness, current source state and policy, and imports its nonce into protected transactional grant state. Reject mismatch/expired/missing grant with no domain effect and a safe actionable error; API owns the exact error enum update.
5. Atomically commit deletion deny state, sanitized receipt/reservation and consumed nonce in the same SQLite transaction. Do not treat unlinking a grant file as atomic consumption. A leftover file cannot authorize a second transaction because the nonce is consumed. Crash before commit gives no deletion and no consumed transaction; revalidate the still-valid grant before retry. Crash after commit yields status/replay of the one effect, not a second grant consumption or effect.
6. Restart invalidates all uncommitted grants through the changed session ID; prepared deletion requires fresh terminal approval. Completed deletion retry recovers a sanitized outcome without new approval or another mutation. Stale target/base/policy or changed plan requires a new reviewed plan and grant. Denial/expiry never becomes implicit approval.
7. Once committed or invalidated, erase review snapshots, grant payload/digest/target mappings and private plan material as part of scrubbing. Retain no content-derived approval digest for a deleted source. Session invalidation and non-reuse of scrubbed operation IDs prevent reauthorization after this erasure. Grant state/files are excluded from export/backups; restored state cannot reactivate them.

A trusted local CLI is preferred to an MCP confirm boolean because the model cannot set it via the five-tool contract. An interactive MCP-host dialog alone is rejected unless the host can independently attest the same owner-bound action; that capability is not assumed. This helper protocol is documentation only and needs API/Reliability schema and crash-order integration before approval.

## Deletion metadata, equality and replay
Whole-input normalized equality is suitable while the request/plan remains eligible. After source deletion, equality fingerprints, request hashes, plan digests and embeddings derived from its content are prohibited retained source metadata, even if salted or named opaque. Encryption does not turn those values into permitted content-free metadata.

For S7, permitted source-specific tombstone fields remain exactly: opaque source reference, deletion status, deletion timestamp and recorded timestamp. No source title/URL/path, body/topic, entity/speaker association, attribution, digest or traceable derivative survives in accessible history/export/logs. Independent recovery-authority integrity/freshness state may have system-level sequence/checkpoint data; it must not encode extra per-source identifying fields.

When an operation/proposal/receipt depended on deleted content:
* Erase original inputs, normalized equality fingerprints, plan body/digest, identity slots/choices, summaries, source-to-entity mappings, id_map, affected changes lists and cached payloads. Trace dependencies before erasing their linkage.
* Reserve its opaque operation ID permanently within the logical installation lineage with deletion/unavailability state and allowed recorded/deletion times only. Do not retain a source-to-person association through an operation receipt. No raw original committed receipt is served.
* For prepare/commit/status on that reserved ID, return content-free REFERENCE_UNAVAILABLE (or API's explicitly equivalent typed unavailable state) before equality matching. Both identical and changed payloads are unavailable and cause zero effects; do not claim REPLAY_CONFLICT can still be established once equality evidence was erased. Never call the model, recreate a plan or execute an old request under that ID.
* Scrub the whole mixed-operation receipt if separating fields would reveal attribution. Undeleted domain records remain intact and inspectable through eligible ordinary reads/queries; loss of the old receipt's detail is disclosed as unavailable. Deletion does not roll back unrelated committed changes.
* Carry sanitized operation reservations through native export/import and reconciled restore. An old B0 receipt/fingerprint is scrubbed by current denials before serving, and old IDs never become fresh operations. Missing authoritative reservation/deletion state blocks mutation recovery/activation; do not silently start a new lineage and call that full recovery.

This deliberately trades exact post-deletion equality/conflict diagnostics for privacy and no repeat effects. It satisfies R4 through distinguishable handling: changed intent is conflict while eligible, and explicitly unavailable once the needed comparison evidence was removed. A genuinely new owner-requested capture uses a new operation ID and fresh authorization. Without retaining content fingerprints the service cannot recognize every manually retyped copy of deleted text; do not claim global semantic duplicate/deletion detection. Restore/import from the old lineage must honor opaque tombstones and reservations, not treat it as fresh owner reentry.

## Host/provider and bounds disposition

# Signed terminal grant reconciliation
Status: security recommendation only; supplements GRO-27 security addendum revision 3876e957-9cd9-4a73-b7bb-c912958f2980. No implementation approval.
Input: GRO-26 coordination comment 073a7fff-1343-499b-a6cc-993b124fc465. The comment proposes a mechanism; it is not evidence of host isolation, provider locality or maintainer approval.

## Disposition
Accept an owner-signed terminal grant as a refinement of the existing local artifact protocol, subject to these requirements. Preserve the exclusive serving lock, one SQLite writer, immutable preview, five-minute maximum grant lifetime capped by plan expiration, random session binding, current-policy validation, transactional consumption and deletion-safe scrubbing already specified.

A signature proves that the enrolled signing key signed the exact grant. It does not by itself prove a human saw the plan or isolate a hostile same-owner process. The operator helper must display the server-produced preview safely and obtain explicit approval through the controlling terminal. It must never sign arbitrary caller-supplied bytes or offer an unattended signing endpoint.

## Key and signed-message boundary
* Owner creates/enrolls an installation-specific signing key through a separate trusted local operator procedure. The service stores only the pinned public verification key and its configuration version in protected control state, not in a restorable data snapshot. Enrollment/replacement/revocation cannot be performed by MCP, model output, a supplied grant or restored database content.
* Keep the encrypted private key owner-only and outside GRM data backups/exports. Unlock only inside the terminal helper; never pass its passphrase through arguments, environment, MCP, model context, logs or an inherited assistant input stream. Do not cache an unlocked signer or passphrase in the serving process. Exit drops unlocked key material; avoid core dumps and private diagnostics. Memory erasure limitations must be documented honestly.
* Use a reviewed standard signature implementation and a fixed, versioned, domain-separated signed-message format. Security recommends Ed25519 with a protected key file; exact encrypted-key container and passphrase protection must be bound by governing architecture before coding. Do not invent encryption or ambiguous ad hoc serialization.
* Sign the exact installation lineage ID, verification-key/configuration version, active server session ID, configured host binding (if any), operation ID, plan ID, canonical plan digest, source target, base revision, current authority/policy epoch, unpredictable nonce, issue time and expiry. Every field is verified against server state. A client label supplied through MCP is not authentication; for this one-session design it must resolve to the protected launch/session binding or be omitted in favor of that binding.
* The full executable plan, not a model-written summary, determines the digest. Signature verification does not waive target/identity validation, eligibility, freshness or stale-plan checks. Unknown format/key versions, bad signatures, expired grants and changed bindings fail with no mutation.
* The helper writes only the owner-protected grant artifact using atomic replacement and durable write. It does not open a second serving or writer connection. The active server verifies and consumes the nonce in the same SQLite transaction as the deletion deny barrier and sanitized receipt/reservation. Leftover files and repeated commits cannot repeat effects.
* Key revocation/replacement increments protected authority configuration, invalidates outstanding grants and requires fresh terminal approval. Restart invalidates uncommitted grants via session change. Restore cannot roll back enrolled verification keys, revocation state or policy epoch. Missing trustworthy current control state keeps activation blocked.

Encryption protects a locked key at rest only to the strength of the chosen container, passphrase and host. A process that can control the owner terminal, change the helper, read unlocked memory or replace protected enrollment state can bypass this design. Do not claim resistance to arbitrary same-UID code execution. The declared host workflow must disable model shell/filesystem/terminal-driving/extension-manager capabilities reaching this control boundary; actual isolation remains unverified.

## Deletion and replay remain unchanged
Grant signatures and digests can link to deleted content; do not preserve them as supposedly content-free tombstones. After deletion, purge grant payload/signature/digest, private preview/plan, request fingerprints and identifying receipt mappings. Retain only the allowed source tombstone fields and content-safe operation reservations described in the prior addendum. Check reserved operation IDs before loading a grant or invoking a model: both identical and changed replay input return committed-unavailable/content-free unavailable with zero further effects. API must bind its precise typed result; no claim of post-scrub equality detection is made.

System-level verification-key configuration is not a per-source deletion record and may persist without source/person associations. Consumed grant detail is not needed once the corresponding operation ID is permanently reserved and cannot be executed again. Reconciled backups/imports must preserve this non-reexecution property.
