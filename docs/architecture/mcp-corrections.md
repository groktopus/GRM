## Decisions and exact behavioral rules
### Operation allocation within the existing status tool
Use the closed StatusInput union below: either allocate:true or operation_id, never both. Allocation returns exactly the Allocated branch wrapped in the existing StatusResult success envelope. It creates no CRM effect and no permanent kit reservation. The status tool now allocates as well as inspects; its whole-tool readOnlyHint and idempotentHint must be false. Losing an allocation reply permits another allocation; it does not justify caller-selected IDs or a sixth tool.

Recommended v1 token: prefix op_ plus unpadded canonical base64url of 59 bytes: version (1 byte), key ID (2 bytes unsigned big endian), server CSPRNG nonce (16 bytes), expiry Unix UTC seconds (8 bytes unsigned big endian), full HMAC-SHA256 (32 bytes). The suffix is 79 characters; schema allows at most 80 for bounded version evolution, while v1 semantic validation requires exactly 79 and canonical re-encoding. Recommend allocation lifetime 900 seconds; expires_at equals its embedded expiry. No caller label or content enters this token.

Recommend a separate protected 32-byte issuance key, distinct from grant signing and kit integrity keys. MAC input is ASCII GRM-OPID-1 followed by LF, then uint16-length-prefixed UTF-8 installation lineage and owner EntityID, then the 27-byte token header. Issuance is owner/installation scoped, not tied to a transient session. No key-ID wrap; retain verification keys for all accepted reservations, or fail closed if unavailable. Security/CTO must review this cryptographic construction before implementation; this document is not a security proof.

Authenticate and validate shape/MAC before permanent storage, logging, model calls or kit append. OPERATION_ID_INVALID omits the invalid argument and returns no echoed canary. Disable raw request/body logging; hashing an attacker-selected label into the permanent kit is also forbidden. Shape validation alone never proves issuance.

For an authenticated token, inspect an existing accepted reservation before applying allocation expiry: accepted IDs remain reserved and recoverable after expiry/restart. A valid unreserved unexpired token yields allocated; a valid expired never-accepted token yields OPERATION_ID_EXPIRED, requiring a new allocation. Invalid/unissued tokens yield OPERATION_ID_INVALID. A validated accepted prepare must durably reserve its ID before preview or any domain effect. The permanent kit contains only validated server-issued tokens and required control metadata, without caller labels. Kit-only reservation after B0 restore returns REFERENCE_UNAVAILABLE and causes no model call or domain effect. Independently known committed-but-scrubbed state yields committed_unavailable. Never recreate a missing operation from its request. Plan expiry does not free the OpID for reuse.

### Receipt readiness and version composition
Keep Receipt.revision as the immutable committed content revision; do not introduce a redundant alias. Add required semantic_readiness (pending/ready/unavailable) and current_index_revision (Version or null). Null is an explicit narrow exception to the prior no-null convention and means no trustworthy published index checkpoint exists. An older published checkpoint may remain non-null during pending/unavailable.

Readiness is evaluated against current eligible content, index generation and policy: pending means coverage is not yet complete; ready means current published coverage includes the committed revision; unavailable means trustworthy coverage cannot currently be established. Clients must not compare opaque revision strings lexically. Replay/status recomputes readiness and current_index_revision without another CRM effect; op identity, committed revision, committed_at and domain changes stay fixed. Ready may regress during outage/rebuild. Deletion filtering precedes receipt presentation. committed_unavailable remains content-free and does not regain scrubbed links through readiness refresh.

Plan.base_revision is GrantVersionToken, matching the grant registry and canonical authorization bytes. Session and base_revision remain mandatory grant bindings. Allocation authentication does not substitute for destructive owner-terminal authorization. The canonical plan digest must include the exact revised plan and bindings.

### Exact versions and export order
ClaimDraft.supersedes and Claim.supersedes become the closed pair {id,version}. Answer fact references also use this pair. No implicit latest-version fallback. ReadInput.version is legal only for entity/fact/commitment and is mutually exclusive with known_at; source/self cannot request a version. Missing or deleted exact versions return the existing safe unavailable outcome.

Each entity/claim/commitment version export carries known_order:{from,until?}. These are monotonic domain-commit sequence numbers within the export lineage, with inclusive from/exclusive until. until exists exactly when that version has known_until, must exceed from, and matches the successor opening sequence. Multiple actions in one atomic commit share its sequence. Enforce safe integer range and fail before exhaustion; no rollover. Timestamps still follow the baseline temporal semantics; sequence order disambiguates multiple versions at the same timestamp rather than rewriting date cutoffs. Validate ordering and lineage across records, beyond JSON Schema.

Extend the closed tombstones-stream record union with ExportUnavailableVersion for entity/fact/commitment exact-version references, without content or evidence. SourceID is deliberately excluded: source tombstones retain only the existing opaque reference/status/timestamp contract and reveal no family or body metadata. The stream registry must explicitly admit this new record; it is not an open arbitrary payload. Closed ExportEntityVersion/ExportClaimVersion/ExportCommitmentVersion definitions below replace their predecessors. Existing closed export manifest fields and other record types remain in force.

### Atomic owner instruction support
For every nondelete mutation with sources absent or empty, preserve the exact owner text as an atomic owner_note source with fixed locator "owner instruction", no normalization, and full codepoint span. Plan.instruction_source identifies that added source. The source, mutation and supporting links commit together or not at all. All allow_new identity slots require creation_evidence; rename and completion actions require evidence too. Exported entity versions carry evidence; empty evidence is allowed only for the explicit bootstrap owner record, enforced semantically. Explicit supplied sources that do not support the requested mutation require clarification/rejection rather than invented provenance.

Automatic instruction copies are dependent provenance, not independent evidence that defeats source-family deletion. In particular, an S7 correction instruction containing the sensitive topic or attribution must inherit the target/support deletion dependencies: deleting S7 must remove that dependent copy and its topic/attribution effects. Data owns the exact lineage/support-selection design. Do not close the deletion oracle merely by declaring this copy an independent source.

Deletion accepts only contract, operation_id, intent:"delete" and exactly one immutable SourceID target. No free-text reason, sources, bindings or instruction owner_note is accepted or retained. Resolve the explicit source target before this typed deletion request; confirmation describes fixed family-deletion scope. Existing grant, preview and digest scrubbing barriers still apply. This narrower request prevents a private deletion reason from entering durable request/plan provenance.

### Topic-support contract binding
Ranking plus citation offsets does not establish topic relevance. The selected bounded support-selection rule, typed plan and lexical tuple are in [retrieval contract](retrieval.md). Only support accepted by that rule may become AnswerItems; retrieval candidates alone cannot become claims. An unavailable selector yields explicit unavailable/partial behavior, not an invented complete-empty result. Complete-empty requires the Data rule to establish the eligible complete scope. Do not introduce an extra model loop, gold-topic labels, or similarity-as-truth to hide this gap. Readiness fields do not resolve ER2/ER3.

## Integrator representation decisions

Select the exact FactVersionRef {id,version} predecessor and exported KnownOrder from this supplement, rather than Data's optional fixed-width Version encoding proposal. Semantic correction also allocates a fresh immutable FactID; predecessor tuple removes any ambiguity, including interval-bookkeeping version. Claim IDs are never reused for another predicate/participants/span/valid value. Entity/commitment logical IDs remain stable across versions. The predecessor's closing known interval is bookkeeping, not a semantic replacement; exact preconditions reject stale/cyclic or multiple-successor corrections. Import preserves every exact tuple and from/until domain sequence.

KnownOrder is global within the lineage, distinct from control sequence. It orders same-second updates; known_at at a UTC second includes all commits at that second within the pinned snapshot. Intermediate same-second versions remain inspectable by exact version and export even when their second-granularity knowledge interval is empty. Validate until/from sequence and timestamp consistency; do not fabricate fractional instants or compare opaque version strings lexically. A restore resumes above the current protected domain watermark; no same-lineage version reuse.

role_at in the MVP denotes explicit exclusive primary employer with exactly one subject person and one organization participant, as defined in retrieval.md; other affiliations use evidenced statement. Overlapping unsuperseded different organizations deterministically produce both conflicting claims, never latest-wins. Each discussed claim has exactly one evidence span and zero/one speaker; source-derived aliases/names and automatic instruction copies retain deletion dependencies. No hidden unexported attribution state is allowed.

All schema-visible new types, errors and readiness fields belong to this initial proposed major1 before its first release; they are not compatible changes to an already shipped API. Any future released-contract change follows the compatibility policy.

## Provenance/export integration

Automatic owner-instruction copies for non-delete changes carry exact upstream target/support SourceID dependencies. Source export rows include required dependencies array (empty only when independent); it is an acyclic current-policy lineage relation, not authority. Deletion of S7 invalidates/purges any such copy containing its topic/attribution and removes false historical support. New names/renames/completion links must be eligible evidence in the same atomic commit; no model-generated paraphrase is persisted as owner instruction. A user-supplied independent source needs explicit independent evidence, not merely a different source ID. Restore/export must not upgrade dependent copy to independent.

Version-specific unavailable markers from the registry carry only opaque exact references/status/timestamps and no link to deleted source or speaker. Deletion sweeps private bodies, aliases/statements/attributions derived solely from removed support, plans/grants/digests, receipts/indexes/model buffers and instruction copies before acknowledging access suppression. Unrelated independently supported entities/evidence remain intact.
